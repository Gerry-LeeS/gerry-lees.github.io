Hashing & Password Cracking —
Hashcat and John the Ripper

Why passwords are hashed instead of stored, how cracking tools work, and what this means from a defender's perspective.

Why Hashing Exists

Storing passwords in plain text is an obvious security failure — if anyone gets access to the database, every credential is immediately exposed. The solution is hashing. When you set a password, the system runs it through a hashing algorithm and stores only the resulting hash. When you log in, it hashes what you typed and compares that to the stored hash. The original password never needs to be stored at all.

This means that even if an attacker gets into a database, all they have is a list of hashes — useless without cracking them first. Understanding how that cracking works is important for defenders, because it directly informs what makes a strong password policy.

The RockYou breach

RockYou was a social gaming company that stored their users' passwords in plain text. When they were breached, around 14 million credentials leaked publicly. That list — rockyou.txt — became one of the most widely used wordlists in security testing precisely because it contains real passwords that real people chose. People reuse passwords, pick their name or hobby, or go with something as simple as "password". A randomly generated password would never appear in that list. A human-chosen one very likely would.

Common Hashing Algorithms

Different systems use different hashing algorithms. Identifying which one you're dealing with is the first step before attempting to crack it. Tools like hashes.com or the hash-id Python script can analyse a hash and return the most likely algorithm.

# Identify a hash using hash-id $ python3 hash-id.py Enter hash: 5f4dcc3b5aa765d61d8327deb882cf99 Most likely: MD5
Algorithm Common use Hashcat -m value
MD5 Legacy systems, file integrity checks 0
SHA-256 General purpose, widely used 1400

Hashcat

Hashcat is a high speed password cracking tool, particularly effective because it can use GPU acceleration to test enormous numbers of passwords per second. The basic syntax follows a consistent structure:

# Basic syntax $ hashcat -m <hash_type> -a <attack_mode> <hashfile> <wordlist> # Example — cracking a bcrypt hash using rockyou $ hashcat -m 3200 -a 0 hash.txt rockyou.txt # Example — cracking a SHA-256 hash $ hashcat -m 1400 -a 0 hash.txt rockyou.txt

The -a 0 flag sets the attack mode to straight — working through the wordlist one entry at a time. The hash type value comes from Hashcat's documentation or from identifying the hash first using hashes.com or hash-id.

John the Ripper

John the Ripper is more versatile than Hashcat and particularly useful for format conversion and cracking specific file types. It can sometimes identify the hash format automatically, though for reliability it's better to specify it explicitly — which is where hash-id becomes useful.

# Basic John syntax $ john --format=<format> --wordlist=<wordlist> <hashfile> # Example — cracking a SHA-256 hash $ john --format=raw-sha256 --wordlist=/usr/share/wordlists/rockyou.txt hash.txt # Windows NTLM hashes use 'NT' format $ john --format=NT --wordlist=/usr/share/wordlists/rockyou.txt hash.txt

Windows and Linux Password Storage

Where passwords are stored matters as much as how they're stored. On Windows, password hashes live in the SAM — Security Account Manager. On Linux, the shadow file holds the hashes, while a separate password file holds account information. Critically, you need root access to read the shadow file but not the password file.

SOC note — privilege escalation

The fact that the shadow file requires root access tells you something important about attacker intent. To get to the password hashes on a Linux system, an attacker first needs to achieve root — through a rootkit, a privilege escalation exploit, or another method. If you're seeing evidence of privilege escalation attempts in your logs, credential harvesting is likely the goal.

John can crack Linux shadow hashes, but first the shadow and password files need to be combined using the unshadow tool. Once combined, John handles the rest automatically.

# Combine shadow and password files $ unshadow /etc/passwd /etc/shadow > combined.txt # Crack the combined file $ john --wordlist=/usr/share/wordlists/rockyou.txt combined.txt

John's Single Crack Mode and Custom Rules

Single crack mode is one of John's more interesting features. Rather than working through a wordlist, it uses the username associated with a hash to generate variations — a technique called word mangling. If a user is called marcus, it will try marcus1, marcus2, M4rcus, marcu$, and so on. To use it, the hash file needs to include the username in front of the hash.

# Hash file format for single crack mode mike:123456789abcdef... # Run single crack mode $ john --single --format=raw-sha256 hash.txt

Custom rules extend this further, letting you define exactly what transformations John should apply. Rules are added to John's configuration file and called by name.

# Custom rule definition [List.Rules:PoloPassword] cAz"[0-9][!£$%@]" # c = capitalise first character # Az = append characters to end # [0-9] = any number, [!£$%@] = these symbols # Use the rule $ john --wordlist=rockyou.txt --rule=PoloPassword hash.txt

Cracking Protected Files

John can also crack password protected zip files, rar archives, and SSH private keys — by first converting them into a crackable hash format using dedicated conversion tools.

# Zip files $ zip2john protected.zip > zip.hash $ john --wordlist=rockyou.txt zip.hash # RAR files $ rar2john protected.rar > rar.hash $ john --wordlist=rockyou.txt rar.hash # SSH private keys $ ssh2john id_rsa > ssh.hash $ john --wordlist=rockyou.txt ssh.hash
Defender use case

These tools aren't only for attackers. During an incident response, an analyst might encounter password protected files left behind by a threat actor — containing malware, exfiltrated data, or tools. Being able to crack those files is a legitimate and useful investigative skill. The same applies to recovery scenarios where access to an encrypted file has been lost legitimately.

Key Takeaways

  • Hashing protects passwords by ensuring the original never needs to be stored — only the hash
  • RockYou exists because real people choose predictable passwords — a randomly generated password is exponentially harder to crack
  • Identifying the hash algorithm before cracking is essential — hash-id and hashes.com are reliable tools for this
  • Windows stores hashes in SAM, Linux in the shadow file — root access is required for the shadow file, making privilege escalation a precondition for credential harvesting on Linux
  • John's single crack mode and custom rules reflect how people actually construct passwords — attackers know this and exploit it
  • zip2john, rar2john, and ssh2john extend John's usefulness into incident response and file recovery scenarios
