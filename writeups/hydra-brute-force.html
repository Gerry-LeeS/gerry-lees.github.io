Hydra — Brute Force Attacks
on Web Forms and SSH

Using Hydra to brute force a web login and an SSH service — and what this looks like from a defender's perspective.

What is Hydra

Hydra is a brute force password attack tool. It automates the process of trying large numbers of passwords against a login service — something that would be completely impractical to do manually. By the time you've typed your second password attempt by hand, Hydra has already tried hundreds.

What makes it effective is threading — running multiple attempts in parallel. By default Hydra uses 16 threads, meaning 16 password attempts are being made simultaneously. Against a wordlist like rockyou.txt with around 14 million entries, this speed matters enormously.

The Objective

The goal of this exercise was to brute force access to a user account called molly — first on a web login page, then via SSH — using the rockyou.txt wordlist. After gaining access to each, the task was to retrieve a piece of data from the target.

Part 1 — Brute Forcing a Web Login

Before running Hydra against a web form, you need to know exactly how that form submits data. Different sites use different field names — one might use username=, another might use user= or usr=. You also need to confirm whether the form submits over HTTP or HTTPS, as these require different Hydra modules.

To find this, I attempted a login with random credentials and used the browser's dev tools to inspect the POST request. This showed the exact field names the form used and confirmed it was HTTP — giving everything needed to construct the Hydra command.

# Brute force a web login form $ hydra -l molly -P /usr/share/wordlists/rockyou.txt 10.10.142.34 \ http-post-form "/login:username=^USER^&password=^PASS^:F=incorrect" -V
Flag / value What it does
-l molly Sets a single known username to target
-P rockyou.txt Uses rockyou.txt as the password wordlist
http-post-form Tells Hydra this is an HTTP POST login form
/login:username=^USER^&password=^PASS^ The login path and exact field names from the POST request — ^USER^ and ^PASS^ are replaced by Hydra on each attempt
F=incorrect The failure string — text that appears on a failed login. Hydra uses this to detect when an attempt has failed.
-V Verbose — shows each attempt as it happens, including which password was tried and whether it failed

Part 2 — Brute Forcing SSH

The second part used the same wordlist to find molly's SSH password. SSH brute forcing follows a simpler syntax since there's no form structure to map out. The -t 4 flag was used to reduce the thread count from the default 16 down to 4, because the target was an older machine that would become overloaded and fail with too many simultaneous connection attempts.

Note on thread count

Reducing threads isn't only about old hardware. Running Hydra at full speed against a real target generates a very obvious pattern in logs — a flood of failed login attempts in rapid succession. A lower thread count is slower but quieter, and less likely to trigger security alerts or lockouts on the target.

# Brute force SSH $ hydra -l molly -P /usr/share/wordlists/rockyou.txt 10.10.142.34 -t 4 ssh # Once the password is found, log in normally $ ssh molly@10.10.142.34

Defender Perspective — What This Looks Like in Logs

A Hydra attack against a login service is not subtle. In server logs it appears as a large volume of failed login attempts from the same IP address in rapid succession. Against a web form, hundreds of POST requests to the login endpoint within seconds. Against SSH, a flood of failed authentication attempts on port 22.

The standard defence is account lockout policy — after a set number of failed attempts within a time window, the account is locked or the IP is rate limited. For example: 5 failed attempts triggers a 5 minute wait, another 5 triggers 10 minutes, then a full account lock. This doesn't stop brute force attempts from happening, but it makes them take so long that a 14 million entry wordlist becomes completely impractical.

SOC note

Brute force attempts are one of the most common and easily detectable attack patterns in logs. A SOC analyst seeing repeated failed logins against the same account or service — especially from a single external IP — should treat it as an active brute force attempt and respond accordingly.

Key Takeaways

  • Hydra automates brute force attacks using threads — massively faster than any manual attempt
  • Before attacking a web form, inspect the POST request in dev tools to find the exact field names and confirm HTTP vs HTTPS
  • The failure string (F=) tells Hydra what a failed login looks like — getting this right is essential
  • Thread count affects both speed and detectability — fewer threads is slower but quieter
  • Brute force attacks produce an obvious log pattern — high volumes of failed attempts in rapid succession
  • Account lockout policies are the primary defence — they make large wordlist attacks impractical by introducing time delays
