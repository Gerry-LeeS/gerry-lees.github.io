Shells —
Reverse, Bind, and Web Shells

How shells work at a technical level, the difference between shell types, a hands-on web shell exercise, and what defenders need to know.

What is a Shell

In an attack context, a shell is a connection between two machines that allows an attacker to execute commands on a target remotely. Getting a shell on a target is often the goal after initial access — it's what turns a vulnerability into actual control.

There are different types of shells, and understanding the difference matters both for offensive techniques and for knowing what to look for as a defender.

Reverse Shell vs Bind Shell

Reverse Shell

The victim machine initiates the connection back to the attacker.

Because the connection comes from inside the target network outward, firewalls and security measures are less likely to block it — outbound traffic is typically trusted more than inbound.

This is the most commonly used shell type for exactly this reason.

Bind Shell

The victim machine opens a port and listens. The attacker connects inward to it.

Because this requires an inbound connection from an external IP, it is more easily detected and blocked by firewalls and security controls.

Less commonly used as a result.

How a Reverse Shell Works

A reverse shell connects two machines together using a pipe with FIFO — First In, First Out. Whatever goes into one end of the pipe comes out the other, in order. The shell runs as a continuous loop.

Understanding stdin, stdout, and stderr is key to understanding how this works:

stdin (0) — standard input. How input enters a system — typically a keyboard. In a shell, this is redirected so that input comes from the attacker's machine rather than a local keyboard.

stdout (1) — standard output. How output is displayed — typically a monitor or terminal. In a shell, this is redirected back to the attacker so they see the results of their commands.

stderr (2) — standard error. How errors are displayed. Also redirected back to the attacker. This matters — if stderr wasn't redirected, error messages would appear on the victim's terminal, potentially alerting them that something was running.

# >& sends both stdout and stderr to the same location # Without this, errors might appear on the victim's screen command >& /location

The loop works like this: the attacker types a command, it is read by the victim machine and executed, the results (stdout and stderr) are sent back through the pipe to the attacker, who then types the next command. This continues indefinitely, giving the attacker an interactive session on the target.

The -i flag makes the shell interactive, and mkfifo creates the named pipe — typically in a temporary directory and called f — that the whole loop runs through.

Web Shells

A web shell is a script uploaded to a web server that allows commands to be executed through a browser. Rather than a direct connection between two machines, the attacker interacts with the target through the web server itself.

The exercise involved a site with a CV upload page. The page accepted file uploads without properly checking what type of file was being uploaded — a security failure known as insufficient input sanitisation. A properly secured upload should only accept the file types it actually needs, such as PDF files for a CV page, and reject anything else.

PHP is commonly used for web shells because it is executed by web servers — when a PHP file is served, the server runs the code inside it rather than just displaying it as text. The <?php ?> tags are what tell the server to execute the contents as PHP code. Without those tags, it's just a file. With them, the server runs whatever is inside.

# Example PHP web shell structure <?php system($_GET['cmd']); ?> # After uploading, navigate to the file in the browser # Then use it to run commands — e.g. cat flag.txt

After uploading the PHP script and navigating to the uploads directory, commands could be run directly on the server. In this case, cat flag.txt with the provided file path returned the required data.

Defender perspective — web shells

The defence against web shell uploads is input sanitisation — restricting uploads to only the file types the application actually needs. A CV page has no reason to accept PHP files. Validating file type on both the client and server side, and storing uploads outside the web root where they cannot be directly executed, are standard mitigations.

Key Takeaways

  • Reverse shells are preferred over bind shells because the victim initiates the connection outward, bypassing most firewall rules
  • stdin, stdout, and stderr must all be redirected correctly in a shell — leaving stderr unredirected could alert the victim
  • A reverse shell runs as a loop via a named pipe — commands go in one end, results come out the other
  • Web shells work because PHP is executed by web servers — the <?php ?> tags trigger execution rather than display
  • Web shell uploads are possible when file upload pages don't properly validate what type of file is being submitted
  • Input sanitisation — only accepting the file types actually needed — is the primary defence against web shell uploads
