Splunk — Tracing a Full Attack Chain
Across Three Log Sources

Starting from a single firewall alert, independently tracing an attack from initial access through reverse shell, privilege escalation, persistence, and data exfiltration across Apache, auth, and firewall logs.

Setup

A multi-source log file was loaded into a local Splunk Enterprise installation containing three log types across a six hour window — Apache web server access logs, Linux authentication logs, and firewall logs. 132 events total, with normal background traffic and a simulated attack sequence embedded within it.

The investigation started from a single simulated L1 SOC alert. All findings were derived independently by searching and reading the logs in Splunk — no hints, no guided tasks.

⚠ Incoming L1 SOC Alert
TYPE: Outbound connection detected SOURCE: 10.0.1.10 (internal server) DESTINATION: 203.0.113.42 (external) PORT: 4444 TIME: 02:14:33

Initial Triage

The first step was scoping the alert — searching all events involving the external IP 203.0.113.42 to understand how much activity there was and when it started.

# Search all events involving the external IP > index=* "203.0.113.42" # 20 events returned # Earliest event: POST request containing netcat in the Apache logs

20 events involving this IP. The earliest log showed a POST request to the web server containing a reference to netcat — a tool used to establish network connections and commonly used for reverse shells. Seeing netcat in a web server access log is an immediate red flag. This is where the attack began.

Note on the source IP

Before tracing the external attacker, the firewall logs showed an earlier connection at 02:13:00 from internal IP 192.168.1.105 to the web server 10.0.1.10 over port 443. Private IP ranges — 10.x.x.x, 172.16.x.x, and 192.168.x.x — are internal network addresses. This means 192.168.1.105 is a device inside the network, not an external one. The attack didn't begin from outside — either a compromised internal machine or an insider threat made the first move.

Attack Timeline

02:13:00
Firewall allows TCP connection from internal IP 192.168.1.105 to web server 10.0.1.10 over port 443.
Internal device initiates contact. Starting point of the attack chain.
02:13:xx
Multiple GET requests to the web server — directory traversal attempting to access /etc/passwd.
passwd contains usernames. The attacker is mapping accounts on the system.
02:13:xx
GET request to /etc/shadow returns 403 Forbidden.
shadow contains password hashes but requires root access. The attacker doesn't have sufficient privileges yet — confirmed by a subsequent whoami command.
02:14:33
Reverse shell established via netcat. Outbound connection from 10.0.1.10 to external IP 203.0.113.42 over port 4444.
Port 4444 is commonly used for reverse shells. The firewall allowed this outbound connection — the shell is now active.
02:14:xx
SSH brute force via the shell against accounts: root, admin, administrator, ftpuser, webmaster, deploy.
Successful login on 'deploy'. The attacker now has an authenticated SSH session.
02:16:04
New user 'svcbackup' created and added to sudo group via /usr/sbin/usermod -aG sudo svcbackup.
Persistence established. The attacker now has a backdoor account with high privileges that will survive a password reset on 'deploy'.
02:16:xx – 05:01:44
Attacker logs in as svcbackup, accesses MySQL files, and exfiltrates data. Session closed at 05:01:44.
Nearly three hours of access to database files. Full scope of exfiltration unknown.

Why Each Stage Matters

The 403 on shadow — attempting to access the shadow file tells you exactly what the attacker wants. Password hashes mean offline cracking, which means potential access to every account on the system including root. The 403 stopped them, but the attempt alone confirms intent.

Netcat in the web logs — netcat is a legitimate networking tool, but seeing it in an Apache access log means it was sent as part of a web request. That's not normal web traffic. It's an immediate indicator of a shell being established.

The svcbackup account — this is persistence. Using the deploy account alone means access is lost the moment that password is changed. Creating a secondary account with sudo privileges gives the attacker a way back in even after the initial compromise is discovered and remediated. It's one of the most dangerous things an attacker can do once inside.

Recommended Response

01 Block external IP 203.0.113.42 at the firewall immediately — cut the active connection
02 Isolate internal server 10.0.1.10 from the network to prevent further lateral movement
03 Disable and delete the svcbackup account — remove the persistence mechanism
04 Reset credentials on the deploy account and audit what it has access to
05 Investigate the internal IP 192.168.1.105 — determine whether it is a compromised machine or an insider threat
06 Review MySQL files for changes, deletions, or signs of exfiltration — assess the full scope of data loss
07 Disable directory traversal on the web server — /etc/passwd and /etc/shadow should never be accessible via web requests

Key Takeaways

  • A single firewall alert was the starting point — cross-referencing three log sources revealed the full attack chain
  • The attack originated from an internal IP — 192.168.x.x is a private range, meaning the threat was already inside the network
  • Netcat in web server logs is an immediate red flag — it should never appear in normal Apache access logs
  • A 403 on /etc/shadow tells you the attacker's intent — they want hashes, which means they want root
  • Persistence via a new privileged account is more dangerous than the initial compromise — it survives remediation
  • Nearly three hours passed between shell establishment and session close — dwell time matters, faster detection means less damage
  • Response order is critical — isolate and cut access first, then investigate, then remediate
