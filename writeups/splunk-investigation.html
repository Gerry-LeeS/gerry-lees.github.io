Splunk — Investigating a
Brute Force Attack and Account Compromise

Setting up Splunk locally, ingesting custom logs, and working through a full SOC investigation workflow from initial search to confirmed compromise.

What is Splunk

Splunk is a SIEM — Security Information and Event Management. It collects logs from all devices, servers, and services on a network and presents them as searchable events. Rather than manually reading through raw log files across dozens of machines, a SOC analyst uses Splunk to search, filter, and correlate events across the entire environment from a single interface.

The events it surfaces — failed logins, successful logins, event log wipes, privilege escalations — are the raw material of a SOC investigation. Being able to query and analyse these quickly is a core analyst skill.

Setup

Rather than waiting for a guided lab, I installed Splunk Enterprise locally, launched it, and accessed Splunk Web via localhost. I then generated a custom auth.log file using an AI-generated scenario — a realistic set of authentication events with a hidden incident embedded in the data — and uploaded it into Splunk as the data source for the investigation.

The scenario: find something suspicious in the login attempts, identify what happened, and determine whether any accounts were compromised.

The Investigation

01 Started with a broad search across all indexed data for failed login events:
index=* "Failed password"
02 Used | stats count to get a total event count — establishing the scale of the activity before digging in.
03 Noticed IP address was not available as a filterable field by default. Created a field extraction for src_ip — mapping the IP address field so Splunk could group and count by it. Field extractions are configured per environment because every organisation labels and structures their logs differently.
04 Ran | stats count by src_ip to see how many failed login attempts each IP address had made. This immediately surfaced the most active attackers as clear numbers — far faster than counting manually through raw events, and practically impossible to do by hand at real log volumes.
05 Added _raw to the search to inspect the raw log lines. Identified brute force behaviour — multiple attempts across multiple usernames within a 15 second window. The speed of attempts made clear this was automated, not manual.
06 Narrowed focus to two specific IP addresses that were repeatedly attempting to access a root account. Searched for "Accepted password" from those IPs and compared against the failed attempts.
07 Identified the pattern — multiple failures followed by a successful login from the same IP against the same account. Confirmed account compromise.

The Finding

Confirmed compromise — 203.0.113.50 → root
FAIL — 203.0.113.50 → root — attempt 1 FAIL — 203.0.113.50 → root — attempt 2 FAIL — 203.0.113.50 → root — attempt 3 FAIL — 203.0.113.50 → root — attempt 4 FAIL — 203.0.113.50 → root — attempt 5 SUCCESS — 203.0.113.50 → root — account compromised

IP address 203.0.113.50 conducted an automated brute force attack against the root account, with all attempts occurring within a 15 second window. After multiple failed attempts, the correct password was found and the root account was successfully accessed.

Recommended Response Steps

In a real environment, the response to this finding would follow this order:

First, isolate the threat — block the attacker's IP address immediately to prevent further access. Second, cleanse the compromised account — rotate credentials, review and revoke any sessions or tokens created during the compromise. Third, investigate what the account did — review all activity from the root account following the successful login, perform file forensics to assess what was accessed, modified, or exfiltrated.

Why root matters

Root is the highest privilege account on a Linux system. A compromised root account means the attacker has unrestricted access to the entire machine — they can read any file, modify any configuration, install anything, or destroy everything. A successful brute force against root is a critical incident.

Key Takeaways

  • Splunk aggregates logs from across an environment into searchable events — essential for SOC work at any real scale
  • Field extractions are required when log fields aren't mapped by default — every environment structures logs differently
  • | stats count by src_ip surfaces attack patterns immediately — manual counting is impractical at real log volumes
  • Multiple failed logins followed by a success from the same IP against the same account is a confirmed brute force and compromise pattern
  • Attack speed is an indicator — 15 seconds across multiple attempts means automated tooling, not a human typing
  • Response order matters — isolate first, cleanse second, investigate damage third
