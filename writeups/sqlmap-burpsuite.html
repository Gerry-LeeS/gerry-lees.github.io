SQLmap & Burp Suite —
Exploiting SQL Injection to Dump a Database

Using Burp Suite to capture a session cookie, then SQLmap to find and exploit a SQL injection vulnerability — from initial access to credential dump.

What is SQL Injection

SQL injection is a technique where malicious SQL code is inserted into an input field to manipulate the database into returning information it shouldn't. Rather than the input being treated as data, the database interprets it as a command. The result can range from leaking usernames and passwords to complete database access.

SQLmap automates this process — testing parameters for injection vulnerabilities and, once found, exploiting them to extract data.

Step 1 — Capturing the Session Cookie with Burp Suite

The target page required authentication to access the vulnerable parameter. Running SQLmap directly against the URL without a valid session would just hit the login page rather than the actual application — the server has no reason to return anything useful to an unauthenticated request.

To solve this, Burp Suite was used as a proxy to intercept the login request. With intercept turned on, a login attempt was made with the target credentials. Burp Suite captured the request mid-flight, exposing the session cookie — proof to the server that the request is coming from an authenticated user.

That cookie was then passed directly into the SQLmap command, allowing it to make authenticated requests against the vulnerable parameter.

Why this matters

Many SQL injection vulnerabilities sit behind authentication. Knowing how to use Burp Suite to capture session tokens and pass them to other tools is a practical skill that goes beyond what most guided labs teach — it reflects how real assessments are conducted.

Step 2 — Finding the Vulnerability

# Run SQLmap against the target with the captured cookie $ sqlmap -u "http://<target-ip>/vulnerabilities/sqli/?id=test" \ --cookie="<captured session cookie>" # SQLmap tests the parameter and confirms it is injectable

SQLmap tested the id parameter and confirmed it was vulnerable to SQL injection. From here, the database could be enumerated systematically.

Step 3 — Enumerating the Database

Database enumeration follows a logical order — you need to know what databases exist before you can look inside one, and what tables exist before you can query a specific table.

01 --dbs — lists all databases available on the server. This gives the full picture of what's there before narrowing focus.
02 -D <database name> — selects a specific database and returns its tables. This is where you identify what data the database holds.
03 -D <database name> -T <table name> --dump — dumps the contents of a specific table. In this case, the users table — returning usernames and hashed passwords.
# List all databases $ sqlmap -u "http://<target-ip>/vulnerabilities/sqli/?id=test" \ --cookie="<cookie>" --dbs # List tables in the target database $ sqlmap -u "http://<target-ip>/vulnerabilities/sqli/?id=test" \ --cookie="<cookie>" -D <database> --tables # Dump the users table $ sqlmap -u "http://<target-ip>/vulnerabilities/sqli/?id=test" \ --cookie="<cookie>" -D <database> -T users --dump

Step 4 — Cracking the Hashes and Logging In

The users table returned usernames alongside hashed passwords. The hashes were cracked using an online hash cracker — the same approach used in the EternalBlue writeup, where Windows NTLM hashes were looked up in precomputed tables.

With the plain text password recovered, logging into the account was straightforward — and the flag was retrieved from inside.

The real lesson — database encryption

The reason the hashes were crackable so easily comes down to weak hashing. A database storing passwords with strong hashing — bcrypt, for example — means that even a complete SQL injection dump doesn't immediately hand over usable credentials. The SQL injection vulnerability and the weak password hashing together are what made this attack successful end to end. Fix either one and the impact is significantly reduced.

Defender Perspective — Preventing SQL Injection

The defence against SQL injection is input sanitisation — specifically, not allowing user input to be interpreted as SQL code. This means stripping or rejecting characters like single quotes that are used to break out of SQL strings, and never allowing raw user input to be concatenated directly into a SQL query.

The correct technical approach is parameterised queries — separating the SQL code from the user input entirely so they can never be combined. No matter what a user types into the field, it is treated as data, never as a command.

Key Takeaways

  • SQL injection inserts malicious code into input fields to manipulate a database into returning data it shouldn't
  • Session cookies are required when the vulnerable parameter sits behind authentication — Burp Suite intercepts them cleanly
  • Database enumeration follows a logical order — databases first, then tables, then contents
  • A successful SQL injection combined with weak password hashing leads to full credential compromise
  • Input sanitisation and parameterised queries are the primary defences — user input should never be treated as a SQL command
  • Strong password hashing limits the damage even when a database is successfully dumped
